# 描述、语义标签与吞吐路线复核

核对日期：2026-10-23。本文为OpenSpec任务10.1的研究与工程建议，不代表新标签器、批量调度或四卡服务已经实现。已有模型选型、许可证与显存估算继续以[研究证据](research-evidence.md#prompt语义标签化模型选型2026-10-22)为准；本篇补充任务边界、误差机制和可执行实验。

本轮只阅读公开论文、官方文档与项目代码，没有读取真实图片、真实描述或OCR，没有下载或运行新模型。下文的项目实测均引用2026-10-22已有记录；新实验方案均标为建议。

## 1. 建议采用的处理关系

保留自然语言描述作为训练条件，另存有证据的语义标签用于检索、分布统计、抽样与审核。长描述绑定实际训练视图；中、短描述分别从同一个已审长描述压缩。把“一次VLM请求生成三档JSON”作为对照方案，而不是直接认定它更快或更准确。先解决重复加载、磁盘提交与批请求，再评估四卡并行。

```text
实际训练视图 → 长描述 → 独立压缩中描述
                    → 独立压缩短描述
                    → 文本事实/语义标签（携带原文证据）

视图级属性（水印、边框、质量等）单独保存
选定描述变体 + 配方明确选取的属性 → 最终训练条件 → 目标tokenizer审核
```

这里的“已审”包含独立的视觉可信度状态。文本压缩与标签抽取只能说明新文本与父文本的关系；父描述若已经误识别，三个后续产物可能一起继承错误。

## 2. 论文中的做法与适用范围

### MOSS：预训练记录与后训练指南分开引用

MOSS报告§3.2、§3.3及附录C.1描述多粒度监督：短句保留主旨，中等描述压缩细节，长描述提供充分信息；普通caption分支在原始/重标注都有效时按20:80采样，三档都有效时等概率选一档，缺失时有回退。该比例是报告的配方，不是本项目最佳比例。附录C.2的JSON、非空字段、几何范围及有限重试检查也不能证明图文事实正确。[MOSS-Image，arXiv v1，2026-10-16，§3.2–3.3、附录C](https://arxiv.org/html/2610.23374v1)

官方后训练指南的“Post-Training → Image Captioning”另给出一次返回`caption.long/medium/short`、`watermark`和`borders`的JSON提示：中描述压缩长描述，短描述概括主体/动作/关系；水印只放独立字段，caption正文保留正常可见文字。它同时建议启用thinking，并给出`max_tokens=16384`的请求示例。因此，缩短预算或关闭thinking属于需要验收的性能实验。指南中的推理负向水印词、独立水印字段、最终训练条件是不同环节；不能由此断言预训练所有caption正文都写了水印。[固定指南版本52b87fc，Image Captioning及Prompt Guidelines](https://github.com/OpenMOSS/MOSS-Image/blob/52b87fca23acedc399d062d593bec388aee9926a/USERGUIDE.md#image-captioning)

本仓库此前分析的35页GitHub PDF固定在`c1355e6`，具有文件SHA和当时版本的阶段表疑点，继续保留原证据。本文新增arXiv v1和后续指南，未证明它们与先前PDF逐字或二进制相同，也不以新网页静默消除旧版本问题。具体版本范围见[既有阅读记录](research-evidence.md#阅读范围与版本)。

### LLaDA：粗分类、描述和图文审核有不同职责

LLaDA-Image附录D的标注输出包含少量领域`tag`、可见文字`render_text`、简短请求式`short_prompt`及客观详细描述`detailed_prompt`；其统一审核提示又分别判断参考文字可用性和caption对图像的忠实度。论文的1–3个领域类别不等于完整的主体、属性、动作、关系标签体系；图文审核也不能用纯文本摘要的一致性替代。[LLaDA-Image v1，2026-09-03，附录D](https://arxiv.org/html/2609.03796v1#A4)

### RECAP与SD3：长度混合和来源混合是两个变量

RECAP用PaLI从图像分别生成长、短描述，并非先生成长描述再逐级缩写；其长描述主要为1–2句话，不能直接对应今天数百token的“long”。SD v1.4实验的表4中，短描述FID为14.85，长描述15.61，50:50混合14.84；语义对象准确率SOA-C分别为79.81、84.59、84.34。混合兼顾两类指标，但没有在每项指标都胜过长描述。它支持测试不同信息粒度，不证明任意数据都应采用固定混合比例。[RECAP，2023-10-25，§4.2–4.3、§6.1、表4](https://arxiv.org/pdf/2310.16656)

SD3用CogVLM重标注并与原始caption按50:50混合；§5.2.2的受控实验中GenEval总分由43.27%升至49.78%，颜色和单物体子项仍有下降。原始/合成来源混合与长/中/短长度混合应分别配置、分别消融。该论文还在冻结编码器后预计算训练表示，属于训练阶段缓存，不能当作caption生成吞吐的证据。[SD3 v1，2024-03-05，§5.2.2、§5.3.1、附录E.1](https://arxiv.org/html/2403.03206v1)

**工程结论：** 不以“描述越长越好”作为目标。需要同时测可见事实的准确性、核心信息保留、训练时长度分布及目标tokenizer容量；生成格式通过、模型指标改善和本项目实际训练收益分别验收。

Florence-2模型卡列出三档caption任务与短语定位；当前`main`还描述了4K上下文继续预训练版本，并提醒训练可能不足。不能把旧论文结果自动赋给不断变化的模型仓库头部；必须固定revision、processor和生成参数。其示例beam设置与JoyCaption采样不同，直接比较“每张耗时”会混入任务差异。[Florence-2官方模型卡：Model Summary、Tasks](https://huggingface.co/microsoft/Florence-2-large)

WD模型卡报告Danbooru划分上的F1=0.4772、阈值0.5296，并支持动态ONNX batch。这些只证明特定评测和接口能力，未给出本项目吞吐或跨领域标签质量。[WD EVA02-Large Tagger v3官方模型卡](https://huggingface.co/SmilingWolf/wd-eva02-large-tagger-v3)

文本模型优先验证已有[选型章节](research-evidence.md#prompt语义标签化模型选型2026-10-22)中的结构化抽取候选，不追加未经比较的“最佳模型”结论。对成人语义只做用户提供文本的中性分类与信息抽取；拒答率、schema有效率、标签准确率、否定识别和未知项保留各自统计。无需通过生成新情节检验分类能力。

|---|---|---|
| 三档及父引用 | 独立状态、缓存和标注身份；中、短分别引用同一父长描述 | 一次VLM三档JSON只是候选路线，尚未进行同集质量/速度对照 |

| 质量审核 | 长描述的视觉可信度和中短文本一致性分开 | 不把集合比较通过或模型自检当作视觉事实合格 |

| 标签 | 已有选型与契约建议 | 尚未部署语义标签器，没有本域标签准确率或中英/NSFW抽取结果 |
| 并行 | 当前build为单执行器、逐阶段逐图；独立DeQA批量实验存在 | 自动批调度、四卡协调、分片合并与完整多卡吞吐未完成 |

### 从长描述压缩时，应分别判断什么

1. **新事实与矛盾：** 子描述出现父描述没有支持的数量、主体、属性、动作或关系，或者改变否定与不确定性，送复核。词面不相同不自动判错，例如合规同义表达需要规范化或语义判定。
2. **核心遗漏：** 预先定义本任务必须保留的主体、动作、主关系和指定文字。短描述省略次要背景是正常压缩，不能按长描述全部事实召回率直接淘汰；需要分别报告核心覆盖率和总覆盖率。
3. **父描述错误：** 子描述完全忠于错误父描述仍然可能视觉错误。这一类只能用图像证据或经授权的独立视觉审核识别。
4. **连锁损失：** 避免`long → medium → short`使第一轮遗漏不可恢复；同一父long的独立压缩保留更明确的来源。一次JSON输出仍有自回归先后依赖，不等于三个结果统计独立。

FaithScore给出“描述片段→原子事实→与图像核验”的评估分解，可借鉴其拆分方法，但本系统的父文本蕴含审核只覆盖其中一部分。让同一个模型自检也存在共同错误，不能冒充独立人工或视觉真值。[FaithScore，EMNLP Findings 2024，方法与摘要](https://aclanthology.org/2024.findings-emnlp.290/)

### 标签契约的最小补充建议

建议先做离线、可回退的文本标签阶段，输出独立产物，不覆盖原caption，也不默认写入训练正文。每个标签至少包含以下字段：

| 字段 | 建议语义 |
|---|---|
| `label_id / taxonomy_version` | 稳定标签ID与词表版本；中英名称可以是显示别名 |
| `caption_id / variant / source_sha` | 精确绑定输入文本及其变体；改写后旧证据失效 |
| `evidence_span` | 原文起止位置及切片校验；明确Unicode码点、左闭右开，避免Python与浏览器UTF-16偏移混用 |
| `polarity` | `affirmed / negated / uncertain`，否定与不确定性不能丢掉 |
| `subject_id / predicate / object_id` | 动作、空间关系和属性绑定到具体实体，避免只有无序词袋 |
| `support` | `explicit_text / inferred / unknown`；默认只将有明确文本证据的项作为可用标签，推断项单独保留待审 |
| `grounding_status` | `not_checked / supported / contradicted / unknown`；文本证据存在不等于图像核验完成 |
| `status / score` | 成功、拒答、缺证据、冲突、待审等状态分开；分数只有校准后才具有门槛意义 |

例如合成文本“桌上有两个杯子，没有花瓶”可支持杯子数量2和“花瓶”为否定提及；标签列表中没有花瓶不能自动等价于“没有花瓶”。“可能是雨天”应保留不确定性。关系标签需要指明谁在谁的左侧；正文没有提供的年龄、身份、来源等事实保持未知。

schema约束可以减少字段缺失和非法枚举，却不能保证事实正确。若采用vLLM，应固定服务版本和对应结构化输出协议；当前文档使用`structured_outputs`或`response_format`，旧`guided_json`等字段已被移除，不能直接复用过时示例。[vLLM Structured Outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/)

## 5. 先解决已测瓶颈，再比较模型服务

以下数字均来自现有[2026-10-22性能报告](https://github.com/lililuya/ImageCaption/blob/d42e84e4abfe7a980b4aaf719f42e9cc8783603a/docs/workbench-v0.4-performance.md)，不是本轮新测速。其他三卡有训练负载，GPU 2用于测试；共享磁盘/CPU并非独占条件。

| 已有观察 | 对下一步的含义 |
|---|---|
| 三档描述仅16张；稳定段长/中/短平均151.2/114.5/69.1 token，合计13.01秒/组三档 | 约277组三档/小时只对应该长度和服务时间；不能充当完整系统或512 token长描述速度 |
| 长描述首请求313.68秒，模型身份核验另265.27秒 | 小批次应先减少不必要重复加载；冷启动与稳定吞吐必须分列 |
| 保留连接后，HDD缓存/checkpoint平均0.94/0.63秒，NVMe约1.14/2.32毫秒 | 优先把状态与缓存放有容量余量的本地SSD，保持FULL提交语义；数据盘与状态盘分别评估 |
| 大图解码由1线程3.07张/秒到4线程9.41张/秒 | 有界预取值得测试，但必须限制内存与同时读盘量 |
| 同一驻留DeQA的batch 1/4请求吞吐0.458/0.728张/秒 | 批量有局部收益证据；约1.59倍而非4倍，评分最大差0.0078125，临界样本需要另审 |

优先级建议如下，均需保持内容不入日志、结果身份独立与恢复语义：

1. **SSD元数据与权重驻留。** 沿用`--state`和`storage.result_cache_root`分盘；同权重、源码、设备及初始化选项复用worker，生成长度/温度等作为逐请求参数。进程复用不能合并长中短缓存和审核身份。先以合成worker验证调用次数、参数隔离和恢复，再以真实GPU数值记录确认收益。
2. **解码预取与阶段内批请求。** 使用有界CPU队列，按图像尺寸、视觉token和输出预算分桶；准确回填每个request ID，保留逐项错误及重试。batch推理不等于把数据库结果放进无界长事务。
3. **兼容的模型服务。** 比较现有transformers worker与支持该checkpoint的vLLM/SGLang路径；先验证processor、聊天模板、停止条件、精度及结构化输出，不因服务名字更快就跳过等价测试。
4. **预算与缓存。** 将通用指令和标签schema放在可复用前缀，测实际缓存命中率；按语义任务约束输出，记录结束原因和截断。输出上限变短产生的“提速”必须和核心信息丢失一起统计。
5. **多GPU。** 在单卡稳定后比较数据分片副本和模型并行，测CPU、磁盘、显存、队列和卡间通信争用，最后验证统一版本提交。

vLLM自动前缀缓存复用相同token前缀的KV，只节省prefill，不加速新token的decode；若主要时间在输出生成，收益可能有限。图像processor缓存、视觉编码结果缓存、KV缓存与本项目结果缓存是不同层级，不能将一次命中推广为所有图像成本消失。[vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)，[vLLM多模态处理设计](https://github.com/vllm-project/vllm/blob/main/docs/design/mm_processing.md)

四张32GB卡不等于单一128GB显存。能连同KV和合理batch余量装进单卡时，优先验证四个独立副本处理不同样本；模型过大或单卡目标batch无法容纳时，再比较两组TP=2或TP=4。并行度、batch token预算、抢占重算都会改变吞吐；这只是实验顺序，不承诺数据并行总优于模型并行。[vLLM Optimization and Tuning](https://docs.vllm.ai/en/latest/configuration/optimization/)

TGI官方已进入维护模式，因此新部署优先考察仍适配目标架构的vLLM或SGLang；现有可用worker仍可保留作基线。HF模型页自动生成的服务启动片段，不足以代替指定版本上的真实兼容测试。[TGI官方维护说明](https://github.com/huggingface/text-generation-inference#text-generation-inference)

E1的B方案可能省去重复输入处理，也可能因更长单次输出、JSON失败整组重试而变慢；两者需要观察。A方案便于只重做失败摘要，但子描述受父long的错误上限约束。不存在只由调用次数就能得出的质量或速度结论。

建议先16条形式冒烟，再固定至少128条进行稳定段比较，至少3次交错顺序运行并报告每轮结果；这些是起步工程规模，不能保证稀有错误覆盖或统计显著性。冷启动单独报告，稳定段不能悄悄删去失败耗时。共享主机先记录其他负载；四卡实跑需要资源窗口，不能中止既有作业来制造独占结果。

### 统一计量与对外报告

主指标建议使用“通过当前验收层级的完整三档图片数/总墙钟小时”，同时显示验收层级：仅形式通过、文本一致性通过、视觉审核通过，不能混在一个成功数里。另报原始输入数、保留率、唯一图片数、各档产物数、重试/拒答/截断和缓存命中率。

性能记录至少分列：模型身份核验、冷加载、排队、读取/解码、prefill、decode、模型后处理、状态提交及导出；无法从provider获得的细项标为不可测，不用总请求耗时伪造拆分。保留输入/输出token及tokenizer身份，跨模型token/s只能辅助解释，不能直接代表同等质量生产力。

质量记录使用预先标注的合成/授权评测集。真实图像语义正确性需要用户或另行授权审核者提供判断，本轮助手只读取数值汇总；没有这类证据时，结论限定为“形式与性能验证”。标签精确率/召回率、关系正确率、否定误识别、核心遗漏分别统计，避免单个总分掩盖严重错误。

## 7. 最小落地范围与后续界线

当前可先落实：同模型worker参数分离和驻留复用；明确当前阶段/当前动作的看板；沿用分盘配置；补齐请求数、实际token和冷启动口径。这些不需要先替换全部模型，但修复收益仍要由对应测试证据支持。

后续按依赖实施：先冻结标签词表与证据契约，再做离线文本标签/摘要对照；随后接批量provider和受控预取，最后接四卡任务租约、幂等结果收集与统一版本提交。新增标签器、自动语义审核、一次VLM三档JSON、批调度及四卡协调分别建可验收任务，不能因本篇研究完成而标为已实现。

文档与合成契约验证只能证明设计或软件行为；真实标签质量、MOSS式采样的训练收益、完整流水线吞吐及四卡扩展效率仍需各自的实验记录。当前不承诺“最佳模型”或“四卡达到四倍”。
